## 2. Question: What Is the Development Framework? Do We Need an Agent Framework?

### Recommended Answer

For the first production build, use a deterministic application workflow, not an autonomous agent framework.

Recommended stack:

| Layer | Framework / Tool | Purpose |
|---|---|---|
| Portal UI | Vue | User-facing Portal screens |
| Backend API | Python, preferably FastAPI or equivalent internal Python web framework | API endpoints for job submission, status, downloads |
| Worker / Orchestrator | Python async worker or containerized job runner | Long-running document parsing, context assembly, Bedrock calls, DOCX rendering |
| LLM integration | AWS SDK / Bedrock Runtime client | Invoke Claude through AWS Bedrock |
| AI workflow | Versioned prompt-chain modules | Constraint extraction -> context assembly -> drafting -> validation -> rendering |
| Agent framework | Not required for MVP | Can evaluate LangGraph/Semantic Kernel later if we move to multi-agent workflows |

The key point: this is not a free-running AI agent. It is a controlled workflow with explicit steps, inputs, outputs, and validation gates.

### Explanation

The architecture already has clear deterministic steps:

1. read SharePoint folder
2. classify and parse files
3. extract constraints
4. assemble context
5. draft issues
6. validate
7. render output
8. store artifacts and audit metadata

An agent framework is useful when the model needs to dynamically choose tools and plan its own steps. Here, the workflow is known in advance and must be auditable. A deterministic orchestrator is easier to test, govern, and explain to audit/security stakeholders.

### Evidence

- Vue is officially described as a progressive framework for building UI, which fits the Portal layer.
- AWS Bedrock can be called directly through AWS APIs/SDKs; we do not need an agent framework to invoke Claude.
- The current architecture proposal defines a fixed AI pipeline: constraint extraction, context assembly, drafting, validation, and rendering.

### Short Message

```text
For MVP, we do not need an autonomous agent framework. We should implement a deterministic Python workflow: SharePoint read -> parse -> context build -> Bedrock Claude draft -> validation -> DOCX render. This is easier to audit, test, and govern. Agent frameworks can be evaluated later if we introduce multi-agent behavior.
```

## 3. Question: Where Do We Define the Guardrails?

### Recommended Answer

Guardrails should be defined in multiple layers, not only inside the LLM prompt.

| Guardrail Layer | Where Defined | Examples |
|---|---|---|
| Input guardrails | Backend API / orchestrator | Validate SharePoint folder, required files, issue input schema, allowed file types |
| Retrieval guardrails | Context assembly module | Only use documents from current project folder; classify Samples as style examples, not evidence |
| Prompt guardrails | Versioned prompt templates | Scope boundaries, citation requirements, tone rules, no unsupported assertions |
| Model guardrails | AWS Bedrock Guardrails, if approved | Content filtering, denied topics, sensitive data controls, policy enforcement |
| Output guardrails | Python validation module | JSON schema validation, citation coverage, scope checks, required fields, warning/error flags |
| Human guardrails | Portal review and IA sign-off | Mark outputs as draft; auditor must review before use |
| Audit guardrails | RDS/S3 metadata | Prompt version, model ID, file versions, validation results, output version |

### Explanation

The most important production guardrails for this project are:

- **scope guardrail:** output must stay inside APM/AWP scope
- **evidence guardrail:** generated statements must cite current-project evidence
- **source guardrail:** Samples are style references, not evidence for current findings
- **format guardrail:** output must match IA issue log structure
- **human review guardrail:** generated report is a draft, not final audit conclusion

Bedrock Guardrails can help with model-level controls, but it should not be the only safeguard. The project also needs deterministic Python validation because audit-specific rules are too domain-specific to leave only to generic model guardrails.

### Evidence

- Amazon Bedrock Guardrails supports applying configured policies to model interactions.
- The architecture proposal already includes deterministic validation outputs such as `validation.json`.
- Audit requirements need traceability, so guardrail versions and validation results should be stored with each run.

### Short Message

```text
Guardrails should be layered. Bedrock Guardrails can be used for model-level controls, but audit-specific guardrails should live in our Python validation layer and versioned prompts: scope check, citation check, required fields, source restrictions, and draft-only human review.
```

## 4. Question: Can CloudWatch Include AI-Related Metrics? How?

### Recommended Answer

Yes, CloudWatch can include AI-related metrics.

We should capture AI metrics in three ways:

1. **Bedrock service metrics and invocation logging**
   - Enable Bedrock monitoring / model invocation logging where approved.
   - Use CloudWatch/S3 destinations carefully because prompts/responses may contain sensitive audit data.

2. **Custom application metrics**
   - The Python orchestrator/worker emits custom metrics to CloudWatch.
   - Use either `PutMetricData` or CloudWatch Embedded Metric Format.

3. **Structured logs**
   - Worker logs include job ID, step name, model ID, prompt version, token usage, duration, and validation counts.
   - Do not log raw prompts or document text by default.

### Recommended AI Metrics

Use a custom namespace such as:

```text
OperationReportJedi/AI
```

| Metric | Type | Example Dimensions | Purpose |
|---|---|---|---|
| `LLMInvocationCount` | Count | `Environment`, `ModelId`, `StepName` | Number of Bedrock calls |
| `LLMInputTokens` | Count | `Environment`, `ModelId`, `PromptVersion`, `StepName` | Input token usage |
| `LLMOutputTokens` | Count | `Environment`, `ModelId`, `PromptVersion`, `StepName` | Output token usage |
| `LLMLatencyMs` | Milliseconds | `Environment`, `ModelId`, `StepName` | Bedrock response time |
| `LLMEstimatedCostUSD` | Number | `Environment`, `ModelId`, `JobId` optional | Cost tracking |
| `ValidationWarningCount` | Count | `Environment`, `ProjectId`, `PromptVersion` | Output quality signal |
| `UnsupportedAssertionCount` | Count | `Environment`, `ProjectId` | Evidence quality signal |
| `CitationCoveragePercent` | Percent | `Environment`, `ProjectId` | Percentage of claims/sections with citations |
| `ContextTokens` | Count | `Environment`, `StepName` | Prompt/context size |
| `PromptTruncationCount` | Count | `Environment`, `StepName` | Detect context overflow |
| `TextractPagesProcessed` | Count | `Environment`, `ProjectId` | OCR volume |
| `ParseFailureCount` | Count | `Environment`, `DocumentType` | Parsing reliability |
| `JobDurationMs` | Milliseconds | `Environment`, `JobType` | End-to-end performance |

Avoid high-cardinality dimensions such as raw user ID, full SharePoint path, full file name, or full job ID for all metrics. Store those details in RDS/job metadata instead.

### Implementation Pattern

In the Python worker:

```text
Before Bedrock call:
  record step_name, model_id, prompt_version, context token count

After Bedrock call:
  record latency, input tokens, output tokens, estimated cost, error status

After validation:
  record warning count, error count, unsupported assertion count, citation coverage

Send to CloudWatch:
  Option A: PutMetricData
  Option B: CloudWatch Embedded Metric Format in structured logs
```

### Evidence

- CloudWatch supports publishing custom metrics using `PutMetricData`.
- CloudWatch Embedded Metric Format lets logs carry metric values that CloudWatch extracts into metrics.
- CloudWatch generative AI observability supports monitoring model invocation performance, including invocation count, token usage, and errors when invocation logging is enabled.
- Bedrock model invocation logging can publish invocation logs to CloudWatch Logs and/or S3, but it is disabled by default and must be configured carefully.

### Short Message

```text
Yes, CloudWatch can include AI metrics. We should emit custom metrics from the Python worker for token usage, Bedrock latency, model calls, validation warnings, citation coverage, and estimated cost. We can use CloudWatch PutMetricData or Embedded Metric Format. Bedrock invocation logging is also possible, but we should be careful because prompts/responses may contain audit-sensitive data.
```

## 5. Question: Access Control - User ID or Service Accounts?

### Recommended Answer

Use both, but for different purposes.

| Area | Recommended Identity | Why |
|---|---|---|
| Portal login | User identity via Entra ID SSO | Know who submitted the job |
| Authorization/audit | User ID stored in backend metadata | Trace who created jobs and downloaded outputs |
| SharePoint access | Prefer delegated user access if feasible; otherwise restricted application permission | Aligns access with SharePoint permissions or approved app scope |
| AWS runtime | IAM roles, not human accounts | Secure service-to-service access |
| Worker execution | Worker service role | Async processing and AWS service calls |
| Support/admin | Separate admin/support roles | Avoid shared accounts and preserve audit trail |

### Explanation

The Portal should capture the real user identity. That identity should be stored in RDS with job metadata and used for authorization checks.

For SharePoint access, there are two possible patterns:

1. **Delegated user permission**
   - The backend reads SharePoint based on the signed-in user's permission.
   - Strongest alignment with user access rights.
   - More complex for async workers because token lifetime/refresh must be handled.

2. **Application permission**
   - The backend app has approved permission to read selected SharePoint locations.
   - Easier for async processing.
   - Must be tightly restricted and approved by Security/SharePoint admins.

For AWS, use IAM roles for the application and worker. Do not use personal AWS admin accounts or shared service account credentials for runtime.

### Evidence

- Microsoft Graph supports both delegated permissions and application permissions.
- AWS services should be accessed through IAM roles with least privilege.
- The architecture requires auditability: user ID, source folder, file references, model version, and output artifact references should be preserved per job.

### Short Message

```text
Use user identity for Portal login, authorization, and audit trail. Use service roles for backend execution. For SharePoint, we need to decide delegated user permission vs restricted application permission with Security/M365. For AWS, the app and worker should use IAM roles, not human admin accounts.
```

## 6. Question: Any Specific AWS Hosting Requirements? Lambda, VM, ECS/EKS?

### Recommended Answer

Recommended first production hosting:

```text
Portal Vue
  -> existing CDL Portal hosting if available

Backend API
  -> Python API container on ECS/Fargate or EKS

Workflow Orchestrator / Worker
  -> Python worker container on ECS/Fargate or EKS

Storage and state
  -> S3 + RDS + ElastiCache

AI services
  -> Bedrock Claude + Textract
```

### Hosting Recommendation by Component

| Component | Recommended Hosting | Reason |
|---|---|---|
| Portal Vue | Existing Portal platform | Aligns with CDL Portal and Entra SSO |
| Backend API | ECS/Fargate container, or EKS if CDL mandates Kubernetes | Stable API service, easier than VM management |
| Worker/orchestrator | ECS/Fargate task/service, or EKS job/worker | Long-running document/LLM jobs fit containers better than Lambda |
| Short utility functions | Lambda optional | Good for small event tasks, not main workflow |
| Database | Amazon RDS PostgreSQL | Durable metadata and audit records |
| Object storage | S3 | Parsed cache and output artifacts |
| Job state | ElastiCache | Live status, locks, progress |
| Logs/metrics | CloudWatch | Operational and AI metrics |

### Why Not Lambda as Main Worker?

Lambda can be useful for short tasks, but the main workflow may include:

- reading many SharePoint files
- OCR/parsing
- multiple Bedrock calls
- DOCX rendering
- retries
- artifact packaging

AWS Lambda has a maximum function timeout of 900 seconds / 15 minutes. That is acceptable for small utility tasks but risky for long-running document workflows. A containerized worker on ECS/Fargate or EKS gives more operational control.

### Why Not VM/EC2 First?

EC2/VM works, but it increases operational overhead:

- patching
- capacity management
- deployment management
- scaling
- host security

For this use case, ECS/Fargate gives container deployment without managing servers. Use EKS if CDL already standardizes on Kubernetes. Use EC2 only if required by internal platform constraints.

### Evidence

- AWS Lambda function timeout can be configured up to 900 seconds / 15 minutes.
- AWS Fargate is a serverless compute engine for containers and works with ECS/EKS.
- Amazon ECS supports running and managing Docker containers, with Fargate available as managed/serverless container infrastructure.

### Short Message

```text
Recommendation: host the Python API and worker as containers on ECS/Fargate unless CDL requires EKS. Lambda is fine for small utility tasks, but not ideal for the main workflow because document parsing + Bedrock calls + DOCX rendering can exceed Lambda's 15-minute limit. VM/EC2 is possible but adds more ops overhead.
```

## 7. Proposed Final Architecture Answer for Infra Team

```text
Development framework:
- Portal: Vue
- Backend/API: Python API service
- Workflow: deterministic Python orchestrator/worker, not autonomous agent framework for MVP
- LLM: AWS Bedrock Claude via AWS SDK

Guardrails:
- Define guardrails in layered controls: input validation, prompt templates, Bedrock Guardrails where approved, Python output validation, and human review.
- Audit-specific checks such as scope, citations, unsupported assertions, required fields, and source restrictions should live in our backend validation layer.

CloudWatch AI metrics:
- Yes, possible.
- Emit custom metrics from worker: token usage, Bedrock latency, model calls, validation warnings, citation coverage, estimated cost, parsing failures.
- Use CloudWatch PutMetricData or Embedded Metric Format.
- Bedrock invocation logging/CloudWatch generative AI observability can also be enabled, but we must avoid logging sensitive prompts/responses unless approved.

Access control:
- Use Entra ID user identity for Portal login, authorization, and audit trail.
- Use IAM roles for AWS runtime services.
- For SharePoint, decide delegated user permission vs restricted application permission with Security/M365.

AWS hosting:
- Recommended: ECS/Fargate containers for API and worker, or EKS if CDL platform mandates Kubernetes.
- Lambda only for short utility tasks, not main long-running workflow.
- Avoid VM/EC2 unless required by internal standards.
```
